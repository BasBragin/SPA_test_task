# SPA Test Task — AI/Data Science

Демонстрационный MVP ИИ-помощника по складскому учёту 
и планированию закупок спа-оператора.

## Требования

- Python 3.11+
- Git


## Проблема (AS IS) и решение (TO BE)

### AS IS

Информация о закупках, расходе, остатках, ценах и сроках годности 
находится в разных источниках и требует ручного анализа. Остатки 
и потребность анализируются вручную, прогноз закупки формируется 
на основе опыта сотрудника и простой оценки среднего расхода. 
В расчёте могут не учитываться открытые заказы, сезонность, 
рост цен, плановая загрузка и сроки годности. Риски дефицита 
и списания выявляются несистемно, а история расчёта и его 
обоснование могут не сохраняться.

### TO BE

- Пользователь открывает MVP и выбирает объект, период 
  и категорию либо задаёт вопрос в чате.
- Система получает данные об остатках, расходе, закупках, 
  ценах, поставках и сроках годности.
- Расчётный модуль прогнозирует потребность и проверяет 
  точку заказа.
- AI-помощник формирует список рисков и рекомендуемый 
  план закупок.
- Пользователь видит объём, стоимость, дату заказа, бюджет, 
  объяснение расчёта и исходные показатели.
- Пользователь может изменить период, бюджетный лимит 
  или другие параметры и пересчитать результат.
- Автоматическое размещение заказа в MVP не выполняется.

### Ключевой принцип

**Агент не придумывает числа.** Все расчёты выполняются 
на структурированных данных и отображаются с указанием 
исходных параметров. LLM (GigaChat) используется **только 
для разбора вопроса**, все вычисления делает детерминированный код.

### Организация данных

В ТЗ данные приходят **одним файлом** (`dataset.json` в корне, 
Приложение 1). В репозитории они **разделены по частям** внутри `src/`:

- `src/part1/dataset_part1.json` — записи движения M1–M8;
- `src/part2/dataset_part2.json` — недельный расход, остатки, 
  поставки в пути;
- `src/part3/dataset_part3.json` — 15 вопросов пользователя.

**Обоснование:** в реальной работе эти данные приходят 
из **разных источников**:
- **Part 1** — из WMS / системы складского учёта (движение товара);
- **Part 2** — из ERP / системы планирования (исторический расход, 
  остатки, открытые заказы);
- **Part 3** — из интерфейса пользователя / CRM (вопросы менеджеров).

Разделение готовит код к **интеграции с разными API** 
(в проде каждый источник — отдельный запрос).

`dataset.json` в корне — **копия всех трёх блоков** для 
соответствия ТЗ. См. также `RESULTS.md`, раздел «Организация 
исходных данных».

## Часть 1: нормализация записей движения товара

**Функция:** `normalize_movement(text) -> dict`

**Что делает:** извлекает 8 полей из текстовой записи:
`date`, `sku`, `location`, `operation`, `qty`, `unit`, `batch`, `doc_no`.

**Метод:** regex + правила + словарь алиасов (без LLM).

**Обоснование:** детерминизм, тестируемость, соответствие ТЗ 
(«не придумывать числа»), fallback без API-ключей.

### Проверка Части 1

```bash
# Одна строка вручную
python scripts/check_normalize.py "05.03.2026 MS-01 приход OIL-001 1 л"

# Несколько строк
python scripts/check_normalize.py --text "строка 1" --text "строка 2"

# Свой JSON
python scripts/check_normalize.py --json my_records.json

# Стандартный dataset из задания
python scripts/check_normalize.py --dataset

# JSON-вывод
python scripts/check_normalize.py --dataset --output-format json
```

### Результат: 8 из 8 записей M1–M8 распарсены корректно

Подробнее — в `RESULTS.md`, раздел «Часть 1».

## Часть 2: прогноз потребности и рекомендация закупки

**Функция:** `forecast_demand(history, sku, horizon_days, params) -> dict`

**Что делает:** прогноз на горизонт, страховой запас, точка 
заказа, рекомендуемая закупка, стоимость, дата истощения, 
уверенность, текстовое объяснение.

**Метод:** **EWMA (α = 0.3)** + **детекция скачков (changepoint)** + 
**линейная интерполяция пропусков**.

**Обоснование:**
1. В данных есть тренд (OIL-001: 8.4 → 13.4 за 12 недель).
2. 12 точек — недостаточно для устойчивой регрессии.
3. Нет годовой сезонности (всего 3 месяца данных).
4. EWMA реагирует на свежие данные, устойчив к шуму.

**Обработка скачка:** `detect_level_shift` находит устойчивый 
рост (×2.26 для SCRB-020) и использует только новый уровень.

### Проверка Части 2

```bash
# Один SKU, 30 дней
python scripts/check_forecast.py --sku OIL-001 --horizon 30

# Все SKU × 2 горизонта
python scripts/check_forecast.py --all --horizons 30 90

# С полным объяснением
python scripts/check_forecast.py --sku SCRB-020 --horizon 30 --explain

# JSON-вывод
python scripts/check_forecast.py --all --horizons 30 90 --output-format json
```

### Результат: 6 прогнозов (3 SKU × 2 горизонта)

| SKU | 30 дней | 90 дней |
|-----|---------|---------|
| OIL-001 | 10 л, 12 590 ₽ | 115 л, 144 790 ₽ |
| SCRB-020 | **36 кг, дефицит 24.09** | 98 кг, 175 371 ₽ |
| WRAP-030 | 0 (избыток) | 37 кг, 90 169 ₽ |

Подробнее — в `RESULTS.md`, раздел «Часть 2».

## Часть 3: разбор вопросов и объяснение ответа

**Функция:** `answer_question(question, context) -> tuple[dict, float, str]`

**Что делает:** разбирает вопрос, вызывает нужную функцию, 
возвращает параметры, уверенность и человекочитаемый ответ.

**Метод:** **GigaChat для NLU** + **fallback на правила** при 
отсутствии ключа + **категориальное меню** как последний резерв.

**Принцип:** LLM **не считает числа**. Она только определяет 
интент и сущности. Все расчёты — через `forecast_demand` и др.

**What-if сценарии:** «+20% загрузка» → `scenario_multiplier = 1.2`. 
Уверенность понижается в 2 раза. В ответе — предупреждение.

### Настройка API-ключа GigaChat (опционально)

Без ключа работает fallback (правила + keyword matching).


Получить ключ: https://developers.sber.ru/studio

## Принципы проекта

### Асимметрия рисков

В системе закупок **дефицит критичнее избытка**:
- **Избыток** → замороженные деньги, риск списания (умеренный риск).
- **Дефицит** → потеря клиента, остановка процедур (критический риск).

**Следствия в коде:**
- Округление закупки **всегда вверх** до упаковки.
- Safety stock рассчитывается консервативно (14 дней).
- При `confidence < 0.6` — флаг «требуется уточнение».
